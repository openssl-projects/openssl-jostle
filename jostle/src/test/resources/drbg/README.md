# CAVP DRBG test vectors (SP 800-90A)

NIST Cryptographic Algorithm Validation Program DRBG vectors. **Public domain**
-- a work of the US federal government, not subject to copyright (17 U.S.C. §105).

- Source: `CAVP-drbgtestvectors.zip` in the standards library, sha256
  `5f7e5658ebd5b4e6785a7b12fa32333511d2acc2f2d9c5ae1ffa16b699377769`, recorded
  in that library's INDEX with its upstream URL.
- Specification: NIST SP 800-90A Rev. 1.

## What is here

`cavp-drbg-vectors.txt`, 156 COUNT blocks, generated by
`tools/generate-drbg-vectors.py`. Do not edit it by hand -- change the script and
re-run it from the repo root:

```
python3 tools/generate-drbg-vectors.py --archive <path>/CAVP-drbgtestvectors.zip
```

or set `JOSTLE_STANDARDS_DIR` to the standards library and omit the flag.

The archive carries 15,840 blocks across three sets (`drbgvectors_no_reseed`,
`drbgvectors_pr_false`, `drbgvectors_pr_true`), 5,280 each. One block is selected
per

    (set, file, mechanism, PersonalizationStringLen, AdditionalInputLen)

for the 13 section headers that map to a registered SecureRandom name: 13 × 4
configurations × 3 sets = 156.

## Why a subset is safe

The selection rule is total and deterministic: the FIRST section in file order
for each key, `COUNT = 0`. The resource carries every selection key and the test
pins the SET of keys rather than the count, so a key that moves, vanishes or
duplicates fails by name.

The generator refuses to write unless the archive's sha256 matches the INDEX row
and the selected keys are exactly the expected 156. See
`jostle/src/test/resources/pkits/README.md` for the corpus where subsetting went
wrong.

## Which headers are absent, and why

The archive's 22 section headers are 8 CTR + 7 Hash + 7 HMAC. Nine do not map to
any name the base provider registers, so no block of theirs is carried:

- `3KeyTDEA use df`, `3KeyTDEA no df` -- no Triple-DES DRBG is registered.
- `AES-128 no df`, `AES-192 no df`, `AES-256 no df` -- every registered CTR name
  carries `useDerivationFunction = true` (see `RandAlgorithm`).
- Hash and HMAC `SHA-512/224`, `SHA-512/256` -- not registered.

JSLFIPS registers four fewer names again (Hash and HMAC `SHA-224` and `SHA-384`),
so its unmapped set is thirteen. Both sets are pinned per provider in the tests,
along with `mapped + unmapped == 22`.

## Format

One block per line, pipe-delimited, fixed 19 columns; absent fields are empty.
The column names are in the file's own header comment. `ReturnedBits` is the
output of the **second** generate call, per the archive's Readme.

The vector file is written with LF endings and pinned to them in
`.gitattributes`; `CavpDrbgVectors` hashes it after normalising line endings to
LF, so a checkout that rewrites them does not break the check.

`MANIFEST.sha256` carries the vector file's sha256 and the source archive's.
`CavpDrbgVectors.load()` checks the vector file against it before parsing, so an
altered or truncated resource is a named mismatch rather than a silent change of
what is under test.
